Open-source India crypto + US stocks tax 
helper: end-to-end plan
Nov 16, 2026  ·  @Reetesh Kumar
1. The plan in one page
Build a free, open-source app that turns messy crypto and US-stock history into the exact
rows the Indian tax return asks for, running on the user's own computer.
Who it is for: Indian residents who trade on Binance or CoinDCX, use EVM wallets, or
hold US stocks.
What comes out: Schedule VDA rows, a TDS total to match with Form 26AS, US stock
gains split into long and short term, a Form 67 worksheet for dividends, and a
Schedule FA worksheet.
How data gets in: exchange export files (main path), any CSV through an AI-written
recipe, read-only API sync for Binance and CoinDCX, and EVM wallet addresses.
Stack: TypeScript, Next.js 16, SQLite, a separate tax-engine package, a local AI model
by default, Docker to run.
Build order: the tax engine and its tests first, then file imports, then API and chain
sync, then US stocks, then public release.
Deadline that matters: returns for tax year 2026-27, the first full year under the new
Income-tax Act, are due 31 July 2027. A usable version by April 2027 catches that
season.
Four hard truths
1. KoinX already sells this from Rs 115. Your only edge is free, private, open and
auditable. Do not try to win on number of integrations.
2. A wrong tax number hurts a real person. A Chartered Accountant must sign off the
rule file and test cases before anyone outside you uses it.
3. Free API tiers shrank through 2026. Etherscan and Blockscout both removed big
chains from free plans. File import has to work perfectly; API sync is a bonus.
4. People open this once a year. It will never be a daily app. Judge it by GitHub stars and
by filings completed, not by daily users.

This section is a build spec, not tax advice. A Chartered Accountant must review the rule
file before any public release.

What the tax return wants (Schedule VDA)
Schedule VDA in ITR-2 and ITR-3 wants one row per transfer, not one net figure
(AllIndiaITR). Each row holds: date of acquisition, date of transfer, head of income (capital
gains or business), cost of acquisition, consideration received, and income. This row
format is the app's main export.

Three rules for every importer
Import twice, get the same ledger. A row with a source_ref already in the ledger is
skipped.
Never throw away the original. The raw row is stored so any number can be traced
and re-imported after a bug fix.
Never guess silently. Anything unclear gets a review_flag, not a made-up value.
7. Tax engine design
The engine is a pure function: ledger rows and a rule file go in, report rows come out. It
never touches the network, so the same input always gives the same tax number.
1. Sort every row by time.
2. Match transfers: a withdrawal from one place and a deposit of the same coin and
amount in another become one "moved" pair, not a sale.
3. Give every row a rupee value, in this order: the trade's own rupee price, then the
trade's USDT price times a rupee rate, then the cached market price. Record which
one was used.
4. Build buy lots for each coin. First-in-first-out is the default. The sources I read name
no required method, so it is a setting.
5. For each sale or swap, use up lots and write one Schedule VDA row: acquisition date,
transfer date, cost, consideration, income.
6. Apply the year's rule file: rate, cess, loss rule, TDS credit.
7. Add up totals and build the reports.
8. Keep the trail: every number links back to the raw rows that produced it.
\text{income}_{row} = \max(\text{consideration} - \text{cost},\ 0) \qquad 
\text{tax} = \sum \text{income}_{row} \times 30\% \times 1.04

Worked example. You buy 1 ETH for Rs 2,00,000 and sell it for Rs 2,50,000. Income is Rs
50,000. Tax is Rs 15,000 plus Rs 600 cess, so Rs 15,600. The exchange already took 1% of Rs
2,50,000 as TDS, which is Rs 2,500, so Rs 13,100 is left to pay. If you also lost Rs 30,000 on
another coin, the tax stays Rs 15,600. The loss does not help.
US stocks use the same engine with a different rule file
Lots are matched the same way, and each sale is marked long-term if held over 24
months.
Long-term gains get 12.5%. Short-term gains and dividends are shown as income only,
because the rate depends on the user's own slab.
Dollars become rupees at the SBI rate for the last day of the month before the sale or
dividend (AllRatesToday).
How we know the numbers are right
Golden cases: about 20 small made-up histories with the correct answer worked out
by hand and signed off by a CA. Any code change that moves an answer fails the
build.
Balance check: coins bought minus coins sold must equal what the exchange or
wallet shows today. A mismatch means missing data, and the app says so loudly.
No negative coins: selling a coin you never bought is flagged as missing history, never
silently given a zero cost.
8. AI CSV import
The AI only writes a small recipe that says which column means what. Normal code then
converts the file. The AI never does maths and never sees the whole file.
1. Read the file's header row and make a fingerprint of it.
2. If a saved recipe matches the fingerprint, use it. No AI call.
3. If not, send the header and the first 20 rows to the model. The screen shows exactly
what is being sent.
4. The model returns a recipe as JSON: date column and date format, buy-or-sell column,
coin, amount, price, fee, and how to split a pair like BTCINR. The reply is forced to
match a schema and rejected if it does not.
5. Code applies the recipe to every row.

6. Checks run: every date parses, every number parses, row count in equals row count
out, no coin balance goes below zero.
7. The user sees 10 converted rows next to the originals and confirms.
8. The recipe is saved. The user can share it to the project's recipe library, so the next
person with that exchange needs no AI at all.
Privacy default: a local model through Ollama, so nothing leaves the computer. A cloud
model is allowed only when the user adds their own key and accepts a warning.
Known traps to handle in code, not by AI:
CoinDCX exports several tabs in one Excel file, so each tab needs its own recipe.
Time zones: the app asks once per file whether times are IST or UTC.
Sign styles: some files show sells as negative amounts, others use a side column.
Fees paid in a third coin, such as BNB.
The recipe library is the long-term asset. Each shared recipe makes the app work for one
more exchange without anyone writing an importer.

Keys and secrets
Ask for read-only exchange keys and say so on the screen where the key is pasted.

Things to ship with the code
A clear "not tax advice" notice in the app and on every report.
A contributor guide focused on the easiest contribution: a new CSV recipe.
Automated dependency updates. The November 2026 Next.js release shows why.
Do not run a public hosted copy at launch. A hosted copy brings back the exact trust
problem this project exists to avoid, and adds security and legal duty you do not need yet.
